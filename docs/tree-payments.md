# TREE payments — staged verification foundation

Status: server-side receipt validation, transactional purchase ledger and an additive database migration are implemented. Both migrations are now applied to the isolated `canopy-checkout-test` preview database branch, not production. Authenticated payment endpoints, signed wallet checkout and recovery are implemented for an isolated preview. Production checkout remains disabled. NFTree access and the live simulated shop are unchanged. Passing receipt validation is **not** permission to apply an upgrade or continue.

## Implemented

`server/payments/tree.mjs` provides a server-owned catalog in integer TREE units and BigInt conversion using verified metadata decimals. Prices match the existing game: Shield 3,000; Fertilizer 5,000; Storm 8,000; Continue 20,000; Guardian growth 5,000; Ancient growth 10,000. Earned Sap remains for planting; NFTree access includes new runs and seasons.

The Mainnet gRPC reader fetches metadata and checkpointed transaction data itself. Its receipt validator requires successful transaction and effects, the authenticated sender, a server-bound digest, the canonical TREE type, an exact matching payer debit and recipient credit, and a checkpoint timestamp after invoice creation; delayed settlement requires an invoice bound before its expiry. It rejects expired invoices even when the invoice expires during the chain lookup. Browser receipt objects, editable TREE balances and pasted digests alone are not payment proof.

A live read-only metadata check returned **6 decimals**. A 20,000 TREE continue therefore costs 20,000,000,000 base units. No wallet was asked to sign or execute a transfer.

## Transactional ledger milestone

`server/payments/ledger.mjs` requires injected trusted authorization, signed-transaction inspection, Mainnet receipt lookup and metadata lookup. It is not callable from the browser. `database.mjs` adapts Netlify Database's pool to parameterized transactions on one leased connection. No HTTP route or automatic payment activation is introduced.

Wallet account and invoice row locks serialize purchases. Repeated/concurrent permanent-growth quotes return the pending invoice. Growth prices use durable species levels, not a browser's claimed level or funds. Signed digests are unique across Canopy invoices. Successful redemption inserts the receipt, advances growth, creates one entitlement and marks payment in one transaction. Retries return the existing entitlement. Supplies/continues have one durable consumption against their server-issued run. New service instances read the same paid records.

Unsigned expired quotes can be replaced. Bound invoices remain reserved for recovery: a payment checkpointed within its original quote window can be verified later, after reauthentication, even when receipt lookup was delayed. Changing the caller's clock does not authorize a late on-chain payment. The default standalone verifier still rejects expired invoices; only the server ledger requests recovery. A transfer executed outside the quote window, or a signed transaction that fails permanently, requires a reconciliation path before checkout activation; the code does not silently delete or release its bound record.

The additive migration is `netlify/database/migrations/20261101023000_canopy_payments.sql`. It creates only the Canopy schema and revokes public access. The existing TREE site reports Netlify Database enabled with no applied migrations. Only read-only hosted status was queried; no hosted rows, schema, deployment, environment variables or other games changed.

Ten local ledger integration tests execute the migration against Netlify's embedded Postgres-compatible engine and cover duplicate/concurrent requests, wallet isolation, receipt replay, cancel/recovery, expired quotes, read failures, logout races, atomic rollback and consumption. Embedded tests serialize transactions internally, so these are not proof of independent PostgreSQL connection contention. A separate CI job runs the same suite against disposable PostgreSQL 16 connections; report its observed result separately. Positive identity, signed-digest and receipt data in ledger tests are fixtures, never a live paid purchase.

Still needed: hosted migration verification, concrete signed-byte inspection and HTTP session adapter, wallet signing/execution and recovery UI, migration of the game from preview spending to authoritative entitlements, failed/stale transaction reconciliation, and actual holder/mobile acceptance. Real TREE payments remain disabled.

## Checkout integration

The new checkout route is hosted inside `canopy-access` at `/play/canopy-defense/api/payments`. It defaults disabled; an authenticated holder can see enabled status. Enabled requests use the same hashed HttpOnly NFTree cookie, origin checks, limited JSON size and strict input fields. The runtime resolves wallet and ownership server-side and rechecks session validity during ledger operations. No payment endpoint trusts a browser wallet, price, receipt or digest.

Wallet checkout selects transferable TREE coin objects, constructs only merge/split/transfer commands, and asks the existing dApp Kit wallet to sign without executing. The server verifies the signature and exact transfer, current coin types/ownership/references, recipient, amount and SUI gas budget. It derives the digest and stores the signed bytes plus binding time before execution. Signed data stays server-side, is never returned in history, and is not a private key. Submission and recovery use those exact bytes, so replaying a request cannot construct another charge. Address-balance-only TREE funds are not supported by this deliberately constrained transfer shape; the UI reports insufficient transferable coin objects without submitting.

The account history offers verification, re-submission of the already signed transaction, recovery of paid items, cancellation of unsigned quotes and reconciliation of a finalized failed transaction. An unknown or unsubmitted transaction is not marked failed merely because indexing is delayed. A bound growth reservation is released only after a definitive checkpointed failure. A payment bound while its quote was valid can settle later; it retains its original server-owned price and its unique digest. Late unsigned quotes cannot bind. This extends the earlier time-window rule to prevent an accepted but delayed submission from losing the purchased item.

Paid gameplay uses a separate local save envelope and server-issued run ID. Preview campaign progress can carry over, but preview TREE and preview growth never become paid credit: wallet balance and durable account growth overwrite them. The server consumes supplies/continues once per original run. Applying a verified item and its local applied-ID marker are saved in one browser write. Lost response recovery returns the same entitlement; fresh battles have new run IDs. Permanent species levels remain in the database. Battle progress is browser-local and editable, with no reward authority; clearing it or abandoning a run does not create refunds or transferable credit. Run-item cross-device battle restoration is not implemented.

`CANOPY_CHECKOUT_ENABLED=true` is an explicit deployment-only opt-in. Production stays disabled until hosted migration, real holder wallet and mobile acceptance are verified. The new `netlify.toml` builds only isolated Canopy previews and blocks ordinary production builds, which would omit the existing arcade's unrelated files/functions. Preview files omit private sources and serve them only through the holder gate. A full production release must preserve all 40 unrelated functions and five schedules plus the existing Canopy gate.

## Canonical checkout preview routing

Wallet acceptance must use `https://tree-token.xyz/play/canopy-defense/checkout-test/`, never the Netlify deployment hostname. A single same-site rewrite serves the isolated checkout build and its API from that path. The backend pins its authentication origin to `https://tree-token.xyz`, uses a dedicated HttpOnly cookie scoped to the checkout-test path, and retains its isolated deployment store/database. It does not trust forwarded-host headers or browser-supplied origins. Regular game sessions and paid test saves remain separate.

`CANOPY_CANONICAL_CHECKOUT_PREVIEW=true` is deployment-only and enables the fixed canonical test adapter; it does not enable checkout by itself. The existing `CANOPY_CHECKOUT_ENABLED=true` opt-in is still required on the isolated build. `tools/release-canonical-checkout.mjs` adds only the rewrite and verifies all existing static file hashes, 41 function identities/configurations, and five schedules. It uses the documented Netlify CLI API surface, with authentication managed by the CLI. No production database migration or application-row changes are part of this routing update.

### Packaging correction

The local `netlify-plugin-canopy-package` build plugin uses the pinned compiler's complete Canopy ZIP in the documented `onPostBuild` event, before upload. It verifies end/central-directory records, every entry's decompressed size and CRC, required entry points, runtime and isolated function identity; then stages that ZIP and its matching routes/rate-limit manifest in Netlify's `FUNCTIONS_DIST`. It never reads CLI credentials or changes other function packages. Local validation passes 164 tests with one Windows-only skip; the actual 676-entry package also passes every CRC check. This corrects the observed CLI packaging artifact without changing game/payment logic or skipping normal database-aware deployment.

A follow-up preview deployment `6ae76995b5e42831ef80a7f3` stopped during plugin loading with `Invalid event 'stageCanopyPackage'`: Netlify treats each entry-point export as an event. The helper is now in `stage.mjs`, with only `onPostBuild` exported by the plugin entry point. A regression check verifies that export boundary. Local validation now passes 165 tests with one Windows-only skip. This correction is pending another deployment; no canonical rewrite or production publication has occurred. The preservation release script also now uses the installed Netlify API client's documented `body` argument for deploy creation and static-file upload.
